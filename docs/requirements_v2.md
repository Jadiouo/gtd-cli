# GTD Task Manager v2.0 產品需求文件（PRD）

## 背景說明

v1.0 的 GTD Task Manager 已成功建立了核心的任務生命週期管理能力——使用者可以快速捕捉、組織並執行任務。然而，隨著使用時間拉長，我們從早期使用者的回饋中發現了幾個顯著的痛點：

首先，任務沒有「截止日期」的概念，導致使用者無法區分哪些任務有時效壓力、哪些可以彈性安排。一個放在 `next-action` 的任務，不論是明天到期還是三個月後到期，在 `list` 畫面上看起來完全一樣，使用者必須靠記憶來判斷輕重緩急，這與 GTD「讓系統替你記憶」的核心理念背道而馳。

其次，使用者在累積了數十甚至數百筆任務後，開始失去對整體工作狀況的掌握感。他們需要知道：「我這週完成了幾件事？」「哪個專案積壓了最多未處理的任務？」「我的 inbox 已經多久沒有清理了？」這些問題目前完全無法透過工具回答。

基於以上需求，我們規劃了 v2.0 的功能延伸。**請注意：v1.0 的所有指令介面、參數名稱、資料欄位均不可更動，v2.0 僅能在既有基礎上疊加新能力。**

## 需求列表

### 需求一：為 `add` 與 `update` 指令加入截止日期支援（修改既有模組）

`add` 和 `update` 指令需要支援一個新的選填參數 `--due`，讓使用者在建立或修改任務時可以設定截止日期。

- `add` 指令加入 `--due` 選項，接受使用者輸入的日期字串；若不提供，任務的截止日期為空（維持 v1.0 行為）
- `update` 指令同樣加入 `--due` 選項，以及對應的 `--no-due` flag（類比現有的 `--no-project`），用來清除截止日期
- Task 的資料結構需新增 `due_date` 欄位，儲存於 JSON 時應向下相容——舊有任務（無此欄位）在讀取時應被視為「無截止日期」，不可因此崩潰
- `show` 指令的輸出需新增一行顯示截止日期（若無則顯示 `(none)`）

日期格式的設計留給學生自行決定，但需在 `--help` 中清楚說明接受的格式，並在輸入格式錯誤時給出明確的錯誤訊息。

---

### 需求二：`list` 指令加入到期篩選與視覺警示（修改既有模組）

`list` 指令需要支援與截止日期相關的篩選與提示，幫助使用者快速識別時效任務。

- 新增 `--due-before DATE` 選項，只顯示截止日期在指定日期**之前（含當天）**的任務；此選項可與現有的 `--status`、`--project`、`--priority` 篩選條件組合使用
- 在 `list` 的表格輸出中新增 `Due` 欄位；無截止日期的任務顯示 `(none)`
- 對於截止日期**已過期（早於今天）**且狀態不是 `done` 的任務，該列的呈現方式需讓使用者一眼察覺異常（具體呈現方式由學生自行設計，可以是前綴符號、文字標記或其他 CLI 可行的視覺手段）

排序規則的調整方式由學生自行設計——需要考量當截止日期與優先度產生衝突時，應如何排序，並在 SDD 中說明設計理由。

---

### 需求三：新增 `report` 指令——工作回顧統計報告（全新功能）

新增一個頂層指令 `report`，讓使用者可以一次性瀏覽整體任務狀況的摘要，取代手動翻查多次 `list` 的繁瑣流程。

`report` 指令不需要任何必填參數，執行後應輸出以下資訊（各區塊的視覺排版由學生自行設計）：

**整體概覽**
- 各狀態（inbox / next-action / waiting / done）的任務數量

**專案分布**
- 列出每個有任務的專案名稱，以及該專案底下各狀態的任務數量
- 無專案的任務單獨列為一個群組（例如標示為 `(no project)`）

**逾期警示**
- 列出所有截止日期已過、且狀態不為 `done` 的任務數量；若無逾期任務，輸出一則鼓勵訊息

`report` 指令需支援一個選填參數 `--project TEXT`，將報告範圍縮限至指定專案。其餘細節（例如是否要顯示最近完成的任務、是否要提示 inbox 堆積警告等）由學生自行決定是否實作，但若有實作需在 SDD 中記載。

---

### 需求四：`remove` 指令加入批次刪除與確認機制（修改既有模組）

目前 `remove` 只能一次刪除一個任務，且沒有任何確認步驟，容易造成誤刪。v2.0 需要在此指令上做兩項改善：

- 支援一次傳入多個 ID 進行批次刪除，例如 `remove --id 1 --id 3 --id 7` 或其他學生認為合理的語法
- 在執行刪除前，輸出即將被刪除的任務清單，並要求使用者輸入確認（確認的互動方式由學生自行設計）；若使用者取消，不刪除任何任務並輸出取消訊息
- 新增 `--force` flag，跳過確認步驟直接執行（適用於腳本自動化場景）
- 若傳入的 ID 中有部分不存在，應明確告知哪些 ID 找不到，並詢問使用者是否要繼續刪除存在的部分；`--force` 模式下則跳過不存在的 ID 並繼續執行，最後彙總輸出刪除結果

## 驗收標準

以下以使用者可觀察的行為描述，作為 v2.0 完成的判斷依據：

1. **截止日期基本流程**：使用者可以在 `add` 時指定截止日期，執行 `show` 後能看到該日期；執行 `update --no-due` 後，`show` 顯示截止日期變為 `(none)`。

2. **舊資料相容性**：將 v1.0 產生的 `tasks.json` 直接給 v2.0 使用，所有指令均能正常執行，不會出現錯誤或崩潰。

3. **`list` 逾期提示**：當清單中存在已過截止日期且未完成的任務時，該任務在 `list` 輸出中能被使用者一眼與其他任務區分；完成後（狀態改為 `done`），該警示消失。

4. **`list --due-before` 篩選**：指定日期後，輸出僅包含截止日期在該日期當天或之前的任務；與 `--project` 組合使用時，兩個條件同時生效。

5. **`report` 基本輸出**：不帶任何參數執行 `report`，能看到所有狀態的任務計數、各專案的任務分布，以及逾期任務的提示。

6. **`report --project` 篩選**：指定專案後，輸出僅呈現該專案相關的統計資料。

7. **`remove` 確認機制**：執行刪除前，使用者會看到即將被刪除的任務列表；輸入取消後，查詢 `list --all` 確認任務仍然存在。

8. **`remove --force`**：加上 `--force` 後，刪除不需要使用者互動即可完成；批次傳入多個 ID 時，結果輸出應清楚列出各 ID 的處理結果。

9. **錯誤處理一致性**：所有新增指令與選項在輸入非法值時，錯誤訊息格式應與 v1.0 保持一致（`❌ Error:` 開頭，對應的 exit code）。
